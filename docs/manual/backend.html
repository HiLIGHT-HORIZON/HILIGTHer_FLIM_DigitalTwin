Backend

Backend module guide

The backend is organised around a single engine, a stable service layer, and support modules for storage, import, profiles, and the event-driven detection core.

twin_engine.py

This is the computational heart of the Digital Twin. It owns the latent decay model, laser profile generation, gate distillation, Fisher Information calculations, Monte Carlo validation, validation-image synthesis, phasors, optimisation, and the approximation bridge to detector event effects.

models.py

Defines configuration and state models. PhysicsConfig is the most important one; it is the contract shared between desktop controls, service API, profiles, decay-model metadata, and MCP.

decay_model_store.py

This registry merges the hardcoded decay families with user-defined custom models. It also carries parameter metadata such as units, sweep defaults, and descriptions so the controller, gridded-MLE summaries, and editor can all stay in sync.

service_api.py

Provides the orchestration layer used by the desktop, HTTP API, and MCP server.

event_driven.py

Hosts the additional event_driven simulation modality. It reuses the same latent optical model but replaces the detection model with an explicit chronological event loop.

Profiles and import modules

profile_store.py persists instrument profiles. instrument_spec_ingest.py extracts profile candidates from external specifications. importers.py handles external data formats such as SDT.

storage.py and sessions

Session save/load functions persist available data products so analysis states can be restored programmatically.
