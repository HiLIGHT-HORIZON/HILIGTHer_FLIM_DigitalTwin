HILIGHTer Digital Twin Manual, API Reference, and MCP Guide

This manual documents the Python Digital Twin as a simulation-first, precision-first FLIM engineering platform. It covers the architecture, service and HTTP APIs, desktop automation interface, MCP surface, prompt pack, and LLM host setup patterns for Codex, Claude, Gemini CLI, and Antigravity IDE.

1. Product Scope

  • Numerical Fisher Information and CRLB estimation for virtual instruments.
  • Monte Carlo validation of Fisher-based predictions.
  • Bootstrap-based estimator-accuracy tests and confidence intervals.
  • Configuration of excitation, detection, gate, and acquisition parameters for instrument design.
  • Synthetic image generation, fitting, diagnostics, and data products.
  • Software interoperability through Python APIs, HTTP APIs, desktop automation, and MCP.
Experimental import may still exist in compatibility paths, but it is not the main product scope of this Python Digital Twin. The platform should be understood primarily as a virtual-instrument and estimator-engineering environment.

2. Architecture Overview

Physics Engine

Forward model for excitation, decay PDFs, gating, Fisher estimation, gridded MLE, Monte Carlo precision workflows, bootstrap statistics, and synthetic image generation.

State Models

Validated configuration and state objects shared across workflows, reports, APIs, and the desktop GUI.

Service Layer

Modulepython/backend/service_api.py

The main reusable orchestration surface. HTTP, MCP, reports, and future integrations should prefer this layer over direct engine access.

HTTP API

Modulepython/backend/main.py

Remote REST interface for workflows, configuration, data products, and diagnostics.

Desktop Workspace

Modulepython/gui/main_window.py

Qt-based engineering workspace for precision, diagnostics, synthetic maps, pixel analysis, and report export.

Desktop Automation

Modulepython/gui/automation_api.py

In-process control surface for the live GUI, intended for Python software embedding or driving the desktop.

MCP Server

Modulepython/mcp_server.py

Stdio MCP server exposing tools, resources, and prompts to LLM hosts using the shared service layer.

Prompt Pack

Modulepython/mcp_prompts.py

Reusable MCP prompt templates for precision audit, instrument design, data inspection, and GUI-oriented guidance.

3. Shared State and Workflow Semantics

The single source of truth is the validated configuration model. The GUI, HTTP layer, report generation, and MCP server all operate on that same backend configuration rather than each owning separate hidden state.

4. Precision Execution Pane

The desktop precision workflow is the main engineering loop. It combines ideal reference curves, theory, optional Monte Carlo validation, bootstrap-based estimator checks, and optional confidence intervals.

11. Prompt Injection Strategy

The prompt pack is defined in python/mcp_prompts.py, with complementary human-readable recipes in docs/llm_integration_prompts.md.

Recommended Agent Sequence

  1. Call get_status and get_config.
  2. Read hilight://gui-schema or call get_gui_schema.
  3. Patch configuration with update_config only after establishing the baseline state.
  4. Use run_precision for theory and MC precision work.
  5. Use data tools such as get_results_snapshot, get_tau_map, get_phasor_map, and get_pixel_analysis for explanation and reporting.
  6. When CI data exists, discuss the interval rather than a single MC trace.
  7. When compatibility flags exist, treat theory-only gains without MC support as tentative.

Core Context Block

You are operating the HILIGHTer Digital Twin through its APIs or MCP server.
Always inspect backend status, current config, and GUI schema before making recommendations.
Treat the Digital Twin as the source of truth for instrument state, diagnostics, precision curves,
Monte Carlo compatibility, bootstrap confidence intervals, and simulated data products.
Distinguish clearly between theory, Monte Carlo validation, and GUI workflow guidance.

12. MCP Smoke Test

A local smoke-test script is included at python/mcp_smoke_test.py. It starts the stdio MCP server, performs initialization, lists tools/resources/prompts, calls representative operations, and checks that the returned surfaces are usable.

python python/mcp_smoke_test.py

The expected checks are:

  • initialize succeeds and returns server info.
  • tools/list, resources/list, and prompts/list all return non-empty surfaces.
  • get_status returns a valid readiness payload.
  • run_precision works with a small theory-only patch.
  • hilight://config and prompt retrieval are readable.

13. Current Limits

  • The MCP server operates on the shared backend service layer, not a live Qt GUI instance.
  • Desktop widget and button execution remain available through the in-process desktop automation API.
  • Experimental import endpoints remain compatibility paths and are not the product center of gravity.
  • For multi-user or remote orchestration, the current global in-memory service state would eventually need explicit session scoping.
